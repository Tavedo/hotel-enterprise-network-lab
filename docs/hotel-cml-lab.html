Hotel Network in Cisco CML
A complete, working hotel enterprise network you build in Cisco Modeling Labs (CML) with real IOS commands. Same shape as the Packet Tracer video you found, but built the enterprise way — VLANs per hotel area, router-on-a-stick inter-VLAN routing, DHCP, SSH, port security, and guest-network isolation that mirrors real PCI segmentation.
CML vs Packet Tracer — read this first
Packet Tracer ships simplified, built-in WAP and wireless-client nodes — drag one on and it "just works" (association, signal, roaming as a light abstraction). That's still the only turnkey, CCNA-scoped wireless experience. CML 2.10+ (2026) added beta wireless, but it's a different model: real Linux-stack nodes (hostapd AP / wpa_supplicant client, plus a newer vAP image), enterprise-scoped, and the simulated APs don't register to the 9800-CL WLC. For this CCNA-level hotel lab we stay on the wired VLAN design — it's simpler, rock-solid, and matches reality: a hotel AP is just a device on an access port set to the Guest or Staff VLAN. A PC on that VLAN stands in for a device that joined that SSID. The switch config is identical either way, so the skill transfers directly.
What you'll build

One hotel building: an edge router doing inter-VLAN routing and DHCP, a core switch, two access switches (ground floor / guest floor), a server, and test PCs representing front desk, a guest device, and management. Six hotel VLANs, full routing between the ones that should talk, and a firewall-style block stopping guests from reaching staff and PMS systems.

Topology

Wiring tip in CML
When you draw a link in CML, it asks which interface on each node. Match the names in the diagram (R1 Gi0/0 ↔ SW-CORE Gi0/0, etc.). IOSv and IOSvL2 both start at GigabitEthernet0/0. Keep a note of which port goes where — it saves confusion later.
How to add a floor
To add SW-FLR2: drop another IOSvL2, trunk it to a free SW-CORE port (e.g. Gi1/0), paste the SW-FD config, change the hostname to SW-FLR2, set the mgmt IP to 10.10.10.5, and set its host ports to VLAN 40 / 50. That's the whole job — the floors are identical by design.
Why this view matters for the interview
You don't need to build the VPN for the CCNA lab, but understanding it answers a classic hotel-IT question: "what happens when the link to HQ goes down?" Answer — staff lose the central PMS, so a good design keeps a local failover PMS running. That's the WAN/VPN concept from the visual training, shown here in CML terms.
Where this fits
These systems don't get built in CML — they're the hotel software that runs over the network. But the mapping matters: the PMS server lives on your VLAN 60, the POS terminals on VLAN 20 (staff), the IP phones on VLAN 30 (voice), the door locks on VLAN 50 (IoT). So the network you built in CML is exactly what carries all of this. That connection — network VLANs underneath, hotel systems on top — is the thing that makes you stand out as someone who understands both layers.

It also makes the guest-isolation story complete: guests must reach the internet but not the hotel's internal systems — and now you can prove both with a single pair of pings. Do it in this order
Build Order
Follow this sequence. Building VLANs and trunks before addressing means links come up cleanly and you can test as you go.
1
Place the nodes
Drag in R1-EDGE (IOSv), SW-CORE, SW-FD, SW-FLR1 (IOSvL2), the PMS-SRV, and your test PCs. Name them as in the plan.
2
Draw the links
Wire exactly as the topology shows. Trunks: R1↔CORE, CORE↔FD, CORE↔FLR1. Access: CORE↔SRV, and each PC to its switch.
3
Start the lab
Start all nodes. IOSv/IOSvL2 take a minute or two to boot. Open the console on each when it's ready.
4
Create VLANs on every switch
Go to the Core SW and Access SW tabs. Create VLANs 10–60 + 99 on all three switches first.
5
Configure trunks
Set the switch-to-switch and switch-to-router links as 802.1Q trunks with native VLAN 99.
6
Configure access ports
Assign each host port to its VLAN (front desk → 20, guest → 40, phone → 30, lock → 50, server → 60).
7
Configure the router
Go to the Router tab. Build the sub-interfaces (gateways), the DHCP pools, SSH, and the default route.
8
Add security
Security tab: the guest-isolation ACL, port security, and SSH on the switches.
9
Test and verify
Verify tab: set PCs to DHCP, ping across VLANs, and confirm the guest PC is blocked from the PMS server.
Golden rule
Build the Layer 2 (VLANs + trunks) completely before the Layer 3 (router). If inter-VLAN routing doesn't work later, 90% of the time it's a trunk that didn't come up or a VLAN missing on one switch — not the router.

Router Configuration

5 · ISP-R1 + Public Server (the "internet" — like the video)

The Packet Tracer video uses two routers: the hotel's EDGE-R1 and a separate ISP-R1 with a public server behind it. That second router is the internet as far as the lab is concerned. It lets you prove two things that matter: inside hosts can reach the outside world, and NAT is hiding your private addresses behind one public IP — exactly what a real hotel edge does. Add a second IOSv (ISP-R1) and a server node (PUBLIC-SRV).

ISP-R1 — the provider router
enable
configure terminal
hostname ISP-R1
no ip domain-lookup
! --- link DOWN to the hotel edge router (the WAN) ---
interface GigabitEthernet0/0
 description LINK-TO-HOTEL-EDGE
 ip address 203.0.113.1 255.255.255.252
 no shutdown
exit
! --- link to the public server (simulated internet service) ---
interface GigabitEthernet0/1
 description PUBLIC-SERVER-LAN
 ip address 198.51.100.1 255.255.255.0
 no shutdown
exit
end
write memory
Why the ISP needs NO route back to the hotel
Notice ISP-R1 has no ip route to 10.10.0.0. That's the whole point of NAT: the hotel's EDGE-R1 translates every internal address to its single outside IP (203.0.113.2), so the public server only ever sees 203.0.113.2 knocking — never 10.10.40.x. The ISP doesn't know, and shouldn't know, your private network exists. That's exactly how a real hotel's internet connection works.

Wire it like the video
EDGE-R1 Gi0/1 ↔ ISP-R1 Gi0/0 (the WAN /30), and ISP-R1 Gi0/1 ↔ PUBLIC-SRV. The part that matters for a hotel
Security — Guest Isolation & Hardening
This is where the lab becomes a real hotel network and not just a routing exercise. The guest VLAN must reach the internet and DNS but must NOT reach staff, PMS, or management — the same segmentation PCI DSS requires. You enforce it with one ACL on the router.
1 · Guest isolation ACL (the key control)

Applied inbound on the guest sub-interface. It allows guests to get DHCP and DNS, lets them reach the internet, but blocks every path into the internal 10.10.0.0/16 hotel network.

R1-EDGE — guest isolation
ip access-list extended GUEST-ISOLATION
 ! allow DHCP to work
 permit udp any any eq 67
 ! allow DNS to the server only
 permit udp any host 10.10.60.10 eq 53
 permit tcp any host 10.10.60.10 eq 53
 ! BLOCK all other access into the hotel's internal network
 deny ip any 10.10.0.0 0.0.255.255
 ! allow everything else (the internet)
 permit ip any any
exit
! apply it to the guest VLAN gateway, inbound
interface GigabitEthernet0/0.40
 ip access-group GUEST-ISOLATION in
exit
Interview-ready explanation
"Guests are on their own VLAN that can reach DNS and the internet but is blocked by an ACL from touching the staff, PMS or management networks. Even if a guest device had malware, it can't reach the systems that handle payments or guest data. That's both good practice and a PCI DSS requirement." — this single control demonstrates you understand hotel network security.
2 · Port security on access ports

Stops someone unplugging a hotel device and connecting their own. Add to host access ports (not trunks):

Access switch — port security
interface GigabitEthernet0/1
 switchport port-security
 switchport port-security maximum 2
 switchport port-security violation restrict
 switchport port-security mac-address sticky
exit
Why maximum 2
Allows a PC plus an IP phone daisy-chained on one port (common in hotels), but no more. restrict drops extra MACs and logs it rather than shutting the port — so a guest plugging in doesn't take down a working port, but you still see the attempt.
3 · Disable unused ports
Any switch — shut unused range
! example: shut a range of unused ports
interface range GigabitEthernet0/4 - 3/3

exit
Hotel security habit
Unused network ports in a hotel (lobby, meeting rooms) should be disabled so no one plugs in and gets onto the network. In the lab it shows you think about physical security — which the Renaissance job description specifically cares about.
4 · Device hardening baseline (paste on every switch & R1)

This is the standard set of global hardening commands a real switch gets before it goes live. None of it changes how traffic flows — it protects the device itself and the people managing it.

exit

CommandWhat it doesWhy it's here (real hotel)
service password-encryptionScrambles plaintext passwords in the configSo a screenshot of show run, or someone glancing at the screen, doesn't leak passwords. Weak cipher, but stops casual exposure.
no ip http server / secure-serverTurns off the switch's built-in web UIYou manage via SSH, not the web page — so disable it. An unused service is just an attack surface and a patching burden.
login block-for 120 attempts 3 within 60After 3 failed logins in 60s, blocks new logins for 120sStops automated password-guessing against SSH. A guest or outsider can't hammer the login.
exec-timeout 10 0Logs off an idle admin session after 10 minIf you walk away from a logged-in console, it won't sit open for someone to hijack.
banner motdShows a warning before loginLegal "authorized access only" notice — a corporate/PCI requirement and it supports action against intruders.
5 · Stop rogue switches — PortFast + BPDU Guard + no DTP

The single most useful switch-security feature in a hotel. A guest room jack, a lobby port, a meeting-room port — any of them could get a cheap router or switch plugged in. These commands make the switch slam that port shut automatically.

All switches — global (recommended)
! make every ACCESS port fast AND self-protecting, in one place
spanning-tree portfast default
spanning-tree portfast bpduguard default
Or per access port (explicit)
interface GigabitEthernet0/1
 switchport mode access
 switchport nonegotiate
 spanning-tree portfast
 spanning-tree bpduguard enable
exit
CommandWhat it doesWhy it's here (real hotel)
spanning-tree portfastPort skips the ~30s STP listen/learn delay and goes active immediatelyA guest's laptop or an AP gets a working link instantly instead of waiting half a minute. Only for ports with an end device, never switch-to-switch.
spanning-tree bpduguard enableIf that port ever receives a BPDU (a message only switches send), it err-disables the portSomeone plugs a switch/router into a room jack → the port shuts instead of letting a rogue device into the spanning tree. This is the rogue-switch defence.
switchport nonegotiateTurns off DTP, the protocol that auto-forms trunksA plugged-in device can't negotiate itself a trunk and suddenly see every VLAN including staff/PMS. The port stays a plain access port.
...portfast default / bpduguard defaultApplies the two above to all access ports from one global commandLess to type, nothing forgotten per-port. It only touches access ports — see the warning below.
The rule you must get right — BPDU Guard goes on ACCESS/edge ports only, NEVER on trunks
Trunk links (switch-to-switch, switch-to-router) legitimately exchange BPDUs — that's how spanning tree prevents loops. If you put BPDU Guard on a trunk, the first normal BPDU would err-disable your uplink and take the whole branch down. The good news: spanning-tree portfast bpduguard default is safe precisely because it only acts on portfast (access) ports and leaves trunks alone. If you set it per-port instead, just never put spanning-tree portfast or bpduguard on a trunk interface.
If a port err-disables
When BPDU Guard trips, the port goes err-disabled and stays down until you clear it: fix what was plugged in, then shutdown / no shutdown the port (or set errdisable recovery cause bpduguard to auto-recover after a timeout). Knowing this answers a real interview question: "a port went err-disabled — what happened and what do you do?"
6 · Add SSH to the access switches

In the build, only R1 and SW-CORE got SSH. The access switches (SW-FD, SW-FLR1) already have a username, enable secret, and a VLAN 10 management IP — they just need the SSH engine turned on so you can manage them remotely instead of only from the console.

SW-FD & SW-FLR1 — enable SSH
ip domain-name hotel.local
crypto key generate rsa modulus 2048
ip ssh version 2
line vty 0 4
 login local
 transport input ssh
 exec-timeout 10 0
exit
end
write memory
Why SSH and not Telnet
transport input ssh means the switch refuses Telnet entirely. Telnet sends your admin password across the network in plaintext — anyone capturing traffic reads it. SSH encrypts the session. On a network that also carries guest devices, plaintext admin access is unacceptable. This is why real switches are SSH-only.
The order these belong in a real build
On a live switch the sequence is: name it → secure access (enable secret, users, SSH, banner) → service password-encryption → build VLANs → trunks (with native 99 + nonegotiate) → access ports (portfast + bpduguard + port-security) → shut unused ports → verify. Security isn't a final step you bolt on — it's woven through the build. That mindset is what separates a technician from someone who just pastes a working config.

12 · Segmentation — three-tier ACL design (guest / voice / IoT)
The design rule
A guest-isolation ACL belongs only on the guest VLAN. Applying it inbound on the voice and IoT SVIs makes those VLANs deny traffic to their own subnet — the door lock pulled DHCP fine but couldn't ping its own gateway (internet still worked, because that line fell through to permit ip any any). Appliances get their own default-deny policy instead: reach the gateway + their server, nothing else.
GUEST-IN — applied on Vlan30 ONLY
ip access-list extended GUEST-IN
 remark ALLOW DHCP
 permit udp any eq bootpc any eq bootps
 remark BLOCK ALL INTERNAL SEGMENTS
 deny ip any 192.168.10.0 0.0.0.255
 deny ip any 192.168.20.0 0.0.0.255
 deny ip any 192.168.40.0 0.0.0.255
 deny ip any 192.168.50.0 0.0.0.255
 deny ip any 192.168.60.0 0.0.0.255
 deny ip any 192.168.80.0 0.0.0.255
 deny ip any 192.168.99.0 0.0.0.255
 remark BLOCK CORE-EDGE TRANSIT
 deny ip any 10.0.0.0 0.0.0.3
 remark ALLOW INTERNET
 permit ip any any
exit
interface Vlan30

exit

ip access-list extended VOICE-IN

HA & Redundancy
The idea
A single core, a single uplink, a single ISP = single points of failure. This layer removes them: a second core with a floating gateway (HSRP), every access switch dual-homed, and two paths out to the internet. The design principle is aggregation / redundancy — if one device dies, the other carries the load with no human intervention.

2 · HSRP — the floating gateway
How it works
Each VLAN gateway becomes a virtual IP that lives on whichever core is active. Clients never change — they still point at 192.168.x.1. Physical IPs: Core-1 .2, Core-2 .3, VIP .1.
L3-CORE (active, priority 110) — per VLAN
track 1 interface GigabitEthernet0/3 line-protocol
!
interface Vlan10
 ip address 192.168.10.2 255.255.255.0
 standby version 2
 standby 10 ip 192.168.10.1
 standby 10 priority 110
 standby 10 preempt
 standby 10 track 1 decrement 30
! repeat for 20,30,40,50,60,80,99
spanning-tree vlan 10,20,30,40,50,60,80,99 priority 4096
L3-CORE-2 (standby, priority 90) — per VLAN
interface Vlan10
 ip address 192.168.10.3 255.255.255.0
 standby version 2
 standby 10 ip 192.168.10.1
 standby 10 priority 90
 standby 10 preempt
! repeat for 20,30,40,50,60,80,99
spanning-tree vlan 10,20,30,40,50,60,80,99 priority 8192
Order matters
Convert Core-1 first (it owns VIP .1 as sole member), then Core-2 joins as standby — otherwise Core-1's static .1 collides with Core-2's VIP. Verify: show standby brief → every VLAN Core-1 Active / Core-2 Standby.
3 · North-south redundancy (dual transit + tracked static)
Why HSRP alone isn't enough
HSRP moves the inside gateway to Core-2, but EDGE still needs a way to send replies back through Core-2. And a bare static route won't fail over — in CML the link stays "up" even when the far node is stopped, so the route never withdraws. The fix is IP SLA + a tracked static: EDGE actively pings Core-1 and pulls the route when it stops answering.
EDGE-R1 — second transit + tracked failover
interface GigabitEthernet0/2
 description INSIDE-TO-CORE2
 ip address 10.0.0.5 255.255.255.252
 ip nat inside
 no shutdown
!
ip sla 1
 icmp-echo 10.0.0.2 source-interface GigabitEthernet0/1
 frequency 5
ip sla schedule 1 life forever start-time now
track 1 ip sla 1 reachability
!
ip route 192.168.0.0 255.255.0.0 10.0.0.2 track 1
ip route 192.168.0.0 255.255.0.0 10.0.0.6 10
Delete the stale specifics
Any old per-VLAN ip route 192.168.x.0 /24 via 10.0.0.2 must be removed — a /24 is more specific than the /16 summary and never fails over. Both ip nat inside (on G0/1 AND G0/2) and ip nat outside (on G0/0) are required.

5 · Next-level resilience (roadmap)
Aggregation is the theme
Everything below follows one rule: bundle or duplicate so one failure is survivable. Add them one at a time — each is a self-contained upgrade.
EtherChannel (LACP) — link aggregation

Bundle two physical links between a switch and a core into one logical Port-channel: more bandwidth and redundancy (lose a member, the channel stays up, no STP reconverge). Highest ROI, costs nothing but one extra link.

Both ends of the bundle
interface range Gi0/2 - 3
 switchport trunk encapsulation dot1q
 switchport mode trunk
 channel-group 1 mode active        ! LACP
!
interface Port-channel1
 switchport trunk native vlan 999
 switchport trunk allowed vlan 30,60,80,99,999
Dual-WAN / dual-ISP — internet redundancy

A hotel's booking & PMS links can't go down, so real sites run a primary circuit + a backup. On EDGE: a second ISP uplink with two default routes, the primary tracked by IP SLA so it fails to the backup automatically — the same pattern you already built for the inside routes.

EDGE-R1 — tracked dual default
ip sla 2
 icmp-echo 203.0.113.1 source-interface GigabitEthernet0/0
 frequency 5
ip sla schedule 2 life forever start-time now
track 2 ip sla 2 reachability
!
ip route 0.0.0.0 0.0.0.0 203.0.113.1 track 2   ! primary ISP
ip route 0.0.0.0 0.0.0.0 198.51.0.1 10          ! backup ISP (floating)
EDGE redundancy — two gateways out

The last single point of failure is EDGE itself. Add a second edge router; the cores point their default routes at a VIP shared by the two edges (HSRP/VRRP on the transit), or each core tracks two edges. Then even a dead edge router keeps the internet flowing.

Node budget
You're near CML's comfortable node ceiling — build these one at a time, or in a cloned lab, rather than all at once. For an interview, being able to describe them ("HSRP on gateways, LACP on uplinks, IP SLA for WAN failover, a second edge for the last SPOF") is worth as much as building every one.
